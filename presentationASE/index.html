2 · Technology stack — Polina

Four services

  • Frontend: React single-page app, served by nginx
  • Backend: FastAPI under /api, with PostgreSQL and a volume for the page images
  • ML backend: a separate FastAPI service that runs the modelone endpoint, called only by the backend
  • Everything in Docker, deployed by Coolify; Traefik routes and adds HTTPS
The overview before each part. The browser only talks to the frontend and to the backend API, on the same domain. The backend owns the data: users, documents, pages and transcriptions in PostgreSQL, and the images on a disk volume. The model runs in its own container, so the heavy ML dependencies stay out of the web backend. Each part has its own Dockerfile, and Coolify deploys them.

2 · Technology stack — Polina

The model: find lines, then read them

  • Goal of the MVP: read a whole handwritten page
  • Kraken BLLA finds the text lines of the pagepretrained default model; fragments on the same baseline are merged
  • TrOCR (trocr-small-handwritten) reads one line at a timeMicrosoft, fine-tuned on English handwriting (IAM)
  • Chosen and tested in a notebook, then moved into the ML backendml-models/english_cursive_mvp.ipynb · story #18
Real BLLA boxes and TrOCR text on english_page_test.jpg
How we chose the model. TrOCR is a line recogniser: it is very good on one line of handwriting, but it cannot read a whole page. So we need a segmenter in front of it: Kraken's BLLA, which ships with a pretrained model and returns one polygon per line. On light cursive it sometimes splits a line in two, so we merge fragments with the same baseline height: here 19 fragments become 9 lines. Both models are pretrained, and we tested the pair in a notebook first. (Polina: add your own selection criteria here.)

2 · Technology stack — Amaury

The backend

  • FastAPI, SQLAlchemy 2 (async) and PostgreSQL 16; Alembic migrations run at startroutes → repositories → models
  • Session login: cookie + CSRF token, passwords hashed with Argon2
  • Upload: the ZIP is checked, the pages go to disk, their metadata to the database
  • Transcription runs as a job: 202 + job id at once, then the client polls the status
The backend is the centre of the app. Route handlers validate the request and hand persistence to repository classes. Login creates a server-side session with a cookie, and every write needs a CSRF token. Uploaded ZIPs are checked for unsafe paths and non-image files; images stay on disk, only paths and sizes go to PostgreSQL. A transcription can take minutes, so the request returns 202 with a job id at once; a background task calls the ML backend page by page, and the frontend polls the job status.

2 · Technology stack — Ali

The ML backend

  • One endpoint: POST /predict with the page imagemodels loaded once at start, weights baked into the image
  • It returns the text, and for each line its box in the image
  • … and a confidence per line and per wordmean probability of their tokens
  • Making it run in Docker: pinned versions, memory limits
Real response for english_page_test.jpg (shortened) · versions and memory: webapp/ml-backend/readme.md
I packaged Polina's notebook as a service with a single endpoint. It takes a page and returns the full text, plus one entry per line with its box and its confidence: that is what makes the frontend view possible. The confidence is the mean probability the model gave to its own tokens; it is not compared to a correct text. Two practical problems: kraken forces torch 2.4, which can't load the usual TrOCR weights, so we pin the safetensors version; and BLLA ran out of memory in a 4 GB Docker VM until we turned oneDNN off.

The frontend is a React and TypeScript app, built by Vite and served by nginx in production. It has login and registration, the document dashboard, upload, and the document page shown here. 3 · User stories — Nicolas

How we manage user stories

  • A GitHub issue with the label User Story, written from the user’s side
  • Always the same template: story, description, acceptance tests
  • Sub-issues are created by team members, because they know what to do within their part of the appFrontend · Backend · ML
  • Done when it meets our Definition of Done
Each user-visible feature is a GitHub issue with the User Story label. The template has three parts: the story in one sentence, a description of what each layer must do, and acceptance tests a teammate can click through. The sub-issues are created by the team members themselves, for frontend, backend and ML, because they know what has to be done in their part of the application. A sub-issue is done only when it meets our Definition of Done: tests, review, docs, and a smoke test on dev.

4 · CI / CD — Nicolas

Git workflow

  • Work on a feature branch from dev: feat/… or fix/…
  • Open a pull request: automatic checks, and a review by a teammate
  • Merged into dev → deployed to the dev site
  • Each Tuesday evening, dev is merged into main → production
Nobody pushes to dev or main directly. A feature lives on its own branch, then goes through a pull request: the CI checks run automatically, and another teammate must approve. The checks are three GitHub Actions workflows, one per part, and only the part that changed is checked: format, lint, tests and a Docker build. Once merged into dev, Coolify deploys it to the dev site, where we test it. Every Tuesday evening dev is merged into main, which deploys production. Commit messages follow a type(scope): description convention.

5 · Outlook — Ali

The second half

  • Information extraction with an LLM: names and dates, shown in the frontend
  • 2–3 models the user can compare and choose fromimprove and benchmark the model (#36)
  • IIIF: open the images to standard viewers; storage on S3 / MinIOfirst draft: PR #55
  • End-to-end and API tests in the pipeline (#54)
The MVP reads the text; the final software should help to analyse it. First, an LLM extracts information such as names and dates from the transcription, and the frontend shows them linked to the text. Second, the user can choose between two or three models and compare them, which means we also need a benchmark. Third, IIIF, the standard for sharing images of heritage documents, with S3-compatible storage. And end-to-end tests, so that the pipeline checks the whole app.
